Human in the Loop MVP - Plan Matching Issue Resolution Notes

Living notes for the plan-vs-code issue cleanup. This file records implementation decisions, spec interpretations, intentional deviations, tradeoffs, open questions, and verification evidence that matter for judging whether the code matches the plan.

Design Decisions

Finalize now preflights affected area pages before mutation

Finalization treats every affected area page as required state. If any affected area page is missing, finalize fails before writing the completed session, creating the delta, updating claims, or committing internal history.

Reason: the plan requires finalized sessions to update affected area pages with recent implementation memory, and .initial-plan/03_REPO_STRUCTURE.md says invalid workspace state must not be silently ignored.

Session-only context derives routing input from session metadata

hitl context --session <id> is interpreted as enough input by itself. The command reads the session spec, task, files, and affected areas, then merges any explicitly supplied task/files as extra routing hints.

Reason: .initial-plan/04_CLI_COMMANDS.md lists --session as a meaningful context option, and requiring --task made that option redundant.

Local site routes use exact route shapes

The server now rejects extra path segments instead of mapping them to a parent page. For example, /areas/source-ingestion/extra should be a 404, not the source-ingestion area page.

Reason: the site spec defines exact route shapes, and loose matching can hide broken generated links.

Routing index IDs are validated before path generation

Workspace validation now checks route index area/task IDs as safe single path segments before using them to build expected content paths.

Reason: malformed persisted workspace state should produce a direct invalid-index error rather than confusing missing-path output.

Spec Interpretations

Area memory link is a finalize invariant

The plan language around finalize was interpreted as an invariant, not best-effort behavior: if a session has affected areas, each affected area must be linkable to the generated delta.

Session metadata is authoritative for context replay

For context --session, the metadata script is treated as the authoritative source for task, files, and affected areas. The command does not scrape freeform HTML card text for routing input.

Validation should fail on malformed indexes, not repair them

Malformed routing-index.json IDs are reported as validation errors. The validator does not rewrite or normalize the index because validation is a gate, not a repair command.

Deviations

db-docs is a post-MVP extension, not part of the original command list

The current CLI includes hitl db-docs and the server includes /areas/:id/database. This extends the original MVP command and route lists rather than replacing them.

Reason: prior work added HITL-native database documentation scaffolding. The extension is kept isolated so the original MVP routes and commands still behave as specified.

Plan issue notes are split from the root implementation notes

This file is maintained as the detailed issue-resolution ledger requested for this cleanup pass. The root implementation-notes.html remains the broad MVP handoff note and points here for plan-matching details.

Reason: keeping the audit-fix trail separate avoids burying concrete plan-matching decisions inside the broader implementation history.

Tradeoffs

Fail hard on missing affected area pages instead of best-effort finalize

Best-effort finalize would keep agents moving, but it risks silently losing the exact implementation-memory link the product is meant to preserve. Failing before mutation is stricter and easier to repair safely.

Merge explicit context input with session metadata

Replacing session metadata with explicit --task or --files would make overrides simple, but it would also let users accidentally drop session context. Merging preserves session state while allowing extra hints.

Exact route matching over permissive fallback

Permissive routes are convenient during manual browsing, but exact routes better expose broken links and better match the route contract in the plan.

Open Questions

Should db-docs be formalized in the product spec?

The command and route exist as an extension. If this is now part of the intended product, the plan/spec files should be updated to include it explicitly.

Should root implementation notes remain the canonical handoff artifact?

The current split is: root implementation-notes.html for broad MVP history, this file for plan-matching issue resolution. Confirm if you want one canonical artifact instead.

Should context --session support replacement semantics?

The current behavior merges explicit inputs with session metadata. If a human expects --task or --files to replace session metadata, that should be specified.
