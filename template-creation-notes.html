Template Creation Notes

Running notes for implementing HITL-native area documentation templates.

Design Decisions

Use one template registry

The five new structures will share evidence handling, area linking, generated-marker overwrite rules, session creation, and internal Git commits. Individual template definitions stay declarative.

Keep db-docs as compatibility wrapper

The existing database scaffold remains available through its current command and API, but the implementation should reuse the generic area-docs pipeline.

Use explicit served routes

Each template gets a known route slug. The server will not serve arbitrary files under /areas/:id.

Use concise route slugs

The new files and routes use api, connectors, retrieval, screens, and ops. This follows the existing database route style and the earlier recommendation instead of mirroring every kind name in the URL. Generated markers still use the exact template kind for force-refresh checks.

Keep generated pages scaffold-only

Templates include evidence inventories, decision surfaces, invariants, known shortcuts, and open questions. They intentionally do not infer API contracts, provider behavior, retrieval quality, UI states, or controls from code automatically.

Spec Interpretations

The requested five templates are interpreted as the five non-database structures previously recommended: API surface, source connector, retrieval, frontend screen, and ops/compliance. Database remains supported because it already exists and becomes the compatibility case for the generic system.

External documentation guidance was interpreted as shape guidance, not as a requirement to copy those documents. API notes separate operation summaries from detailed contracts and error behavior; connector notes capture sync/cursor/rate-limit assumptions; retrieval notes separate retrieval and answer evaluation; frontend notes force state/accessibility coverage; ops notes connect alerts, telemetry, and runbooks to operating decisions.

Deviations

The implementation adds one generic area-docs command instead of five separate commands, because the templates differ in content but not lifecycle. hitl db-docs remains as the specific compatibility command.

Some review feedback suggested route/file names like api-surface.html. The implementation keeps concise filenames such as api.html and connectors.html to match the database route pattern and the earlier recommendation, while the generated marker records the exact full template kind.

Tradeoffs

Generic command vs aliases

A single hitl area-docs --kind command is less discoverable than five command names, but avoids duplicated CLI plumbing and keeps new template kinds cheap to add.

Scaffold, not reverse engineering

The templates inventory evidence and prompt the architect/reviewer to fill facts. They intentionally do not infer schema, API contracts, or RAG behavior from code automatically.

One e2e smoke path

Unit tests cover all five template kinds. The e2e suite exercises one representative area-docs path to prove CLI, route serving, area linking, session context, and internal history without making the catch-all e2e test much larger.

Open Questions

Should the CLI eventually expose friendly aliases such as hitl api-docs and hitl connector-docs, or is the generic registry command the preferred public surface?

Should frontend-dashboard later be renamed or supplemented if frontend screen notes prove broader than dashboard work?
